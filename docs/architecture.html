Personal Knowledge Base · architecture walkthrough

How a saved article becomes searchable

One click in the browser sends a page to a local FastAPI app. The app turns it into a summary, an embedding and a few tags, and stores it in OpenSearch. The web app, scripts and any AI chat (over MCP) then search the same store through the same code. Coding agents use the same door to save a summary of a session when the owner asks for one.

1 · System overview

Five clients, one app, one database

Everything runs on the owner's machine in two Docker containers, published on localhost only. Every client signs in with the same API_TOKEN.

Browser extension

Runs Mozilla Readability inside the tab and sends the article HTML as you see it, so logins, paywalls you passed and consent walls don't matter. Optional tags and a private note go with it.

Web app

React + TypeScript over the JSON API. Logs in once with the token, which then lives in an HttpOnly cookie; every request adds a CSRF header that other sites cannot send.

The app

FastAPI with background tasks. It holds every rule (versions, tags, re-tags); the clients only hold view state. No agent framework, only plain HTTP calls to the LLM.

Coding agent

Nothing of ours runs beside it. A skill made of instructions tells the agent what to write, and one MCP call does the rest, so it needs no knowledge of the folder or the file format.

OpenSearch

The only database. Chosen for its built-in hybrid search (keywords + vectors in one query). Three indices, strict mappings, data in a Docker volume. Session Summaries are the one exception to its being the record: their files are.

2 · Capture pipeline

From the Capture button to a tagged, searchable Item

The request does only the cheap work and answers 202 right away. The three LLM calls run in a background task, so the popup never waits for the model.

One Item per URL

The URL is normalised first (lowercase host, no trailing slash, tracking parameters such as utm_* removed, query sorted). Its SHA-256 is the Item id, so the same article saved twice lands on one Item with two Versions.

Tags only from the taxonomy

The tag prompt lists the owner's tag paths with descriptions. Paths the model invents are dropped. Tags the owner removed from this Item are never offered again, and neither is any Project (a tag under project/). An empty taxonomy means no tag call at all.

Every result records how it was made

Each Version stores the model, prompt version, embedding model and taxonomy version it was produced with. That is how the pipeline knows when an old summary can be reused and which Items a re-tag should visit.

3 · Search

Keywords and meaning in one query

The search box and the MCP search tool run the same function. One embedding call per search, unless it looks in a single section of Session Summaries; OpenSearch does the rest.

Search in one section

With the Sessions kind, search can look in Decisions or Problems alone (section on the API and the MCP tool). That is keywords only and costs no embedding call: a Session has one embedding for its whole summary, so meaning cannot be narrowed to a section.

Which line matched

The Item keeps a Session's Decisions and Problems line by line, and every search returns the lines holding the query's words. A Session found by meaning alone may have none. Common words count here, as they do in keyword search.

4 · Storage model

History in one index, the current view in another

Versions are never updated in place. Each capture or re-tag appends a new one, and the Item document is overwritten with a copy of the newest. Search reads only items, so there is no "is current" flag to filter on.

5 · MCP server

Any AI chat can use the knowledge base

The app serves an MCP endpoint at /mcp (streamable HTTP, stateless, behind the same bearer token). Agents get five tools that call the same functions the web app uses, so an agent cannot do anything the owner couldn't do in the UI.

Register it in Claude Code

One command while the app runs. Then ask "what do I have on Hamilton from this week?" or "save this as a Thought".

Agents stay outside the pipeline

The capture steps are known in advance, so they run as fixed code. Open-ended work (researching around an Item, proposing tags) belongs to an agent that calls these tools.

6 · Session Summaries

What a coding session decided, findable months later

When the owner asks, the agent in a Claude Code or Codex session writes down what was decided and fixed, and sends it in one MCP call. Whole conversations stay in the agent's own files; only the summary enters the knowledge base. There is no hook and no reminder: whether a session matters is the owner's call.

What a summary holds

Title and status (done, partial, blocked, abandoned), then Goal, Outcome, Decisions with their reason and rejected alternative, Problems with cause and fix, Dropped, Todo, Sources and Keywords. Empty sections are left out, so a small session stays short.

One Item per session

Summarising the same session again adds a Version and a new file, since the agent and its session id stay the same. The summary is read-only in the knowledge base; the owner's note and tags stay editable, because they never reach the file.

Projects

A session's only tag is its Project, a tag under project/. projects.yaml, kept beside the summaries, maps a folder to one. It fills up as the owner answers, and no LLM ever picks a Project.

Back to the conversation

A Session's page in the web app shows the command that resumes it in the folder it started in, such as claude --resume <id> or codex resume <id>, plus the path of its transcript.

Past sessions

The same skill can summarise an old session from its transcript. The result is marked as written after the fact, and it is dated the day it was written.

Install the skill by linking it from the root of a clone, here for Claude Code. For Codex, link it into ~/.codex/skills instead and register the server with codex mcp add; the README has both.

ln -s "$PWD/agent/skills/session-summary" ~/.claude/skills/session-summary

7 · Design decisions

Why it is built this way

Each of these is an architecture decision record in docs/adr/.

  1. ADR-0001
    OpenSearch is the only database

    Its hybrid search pipeline was the deciding feature, and one store is what a self-hoster can run. Considered: Postgres with pgvector, Meilisearch, Qdrant. Cost: the embedding is stored twice per Item (about 6 KB).

  2. ADR-0002
    Versions keep the summary, not the full page

    Summarise reads the page once; tagging reads only the summary, so the taxonomy can change and Items be re-tagged without fetching again. Cost: an old Version can't be re-summarised with a better model. Thoughts are the exception and keep their full text.

  3. ADR-0003
    No agent framework in the capture path

    v1 used a LangChain agent. v2 is a fixed Python pipeline with two structured-output calls and one embedding call through a thin adapter: deterministic, faster and cheaper. Automation goes through MCP.

  4. ADR-0004
    The web UI is React over the JSON API

    The three-pane layout with search as you type outgrew Jinja and htmx. The new app talks only to the same JSON API as the extension and the MCP server; the backend stays the single place for every rule.

  5. ADR-0005
    Summary Files are the record for Sessions

    An exception to ADR-0001, so summaries stay readable outside the knowledge base and its Sessions can always be rebuilt from the folder. Considered: the knowledge base as the only copy, and the agent writing the file itself. Cost: a summary exists twice, and the file wins on any disagreement.
